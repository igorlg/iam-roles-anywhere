# Security

This document describes what this tool protects, what it does not, and where the
remaining sharp edges are. It is written to be useful when deciding whether to
deploy it, not to reassure.

## Reporting a vulnerability

Open a GitHub issue for anything already public, or anything that only affects a
local development setup.

For an unpatched vulnerability that could affect deployed users, please use
GitHub's private vulnerability reporting on this repository
(**Security → Report a vulnerability**) rather than a public issue. Include the
version (`iam-ra --version`), the CA mode (self-signed or ACM Private CA), the
key store in use, and the smallest reproduction you have.

This is a personal project with no SLA. Expect best-effort, not same-day.

## What the system is

Hosts authenticate to AWS with an X.509 client certificate. IAM Roles Anywhere
validates the certificate chain against a **trust anchor**, then issues temporary
credentials for a role. Authorisation is the composition of three things:

1. the certificate chains to the trust anchor,
2. the IAM role's trust policy permits `rolesanywhere.amazonaws.com` to assume it
   (optionally narrowed to a certificate subject CN), and
3. the host's Nix configuration names a profile ARN and role ARN to request.

A certificate carries **no role information**. It identifies a host. This matters
for reasoning about compromise: stealing a host's key gets an attacker every role
whose trust policy accepts that certificate, not just the roles the host happened
to be configured with.

## Trust boundaries

| Asset | Where it lives | Who can use it | Blast radius if stolen |
|---|---|---|---|
| CA private key (self-signed mode) | admin workstation, on disk | anyone who can read the file | **total** — mint a certificate for any host, assume any role in the scope |
| CA private key (ACM PCA mode) | AWS HSM, non-exportable | anyone with `acm-pca:IssueCertificate` | total, but requires an AWS API call that is logged in CloudTrail |
| Host private key | the host that uses it | with `files`: anyone who can read the file. With `macosKeychain`: no one — non-extractable | that host's identity, and every role accepting its certificate |
| Host certificate | the host, your Nix repo, anywhere | public | none — it is not a secret |
| CSR | anywhere | public | none |
| `iam-ra` state document | S3, plus a local cache | `s3:GetObject` on the bucket | metadata only: hostnames, role names, ARNs, serials. No key material |

The CSR and the certificate being public is the load-bearing property of the v3
design. It is what allows enrolment across a trust boundary with no secure
channel: you can email a CSR, paste it into a ticket, or commit it to a public
repository without consequence.

## What v3 changed

v2 generated each host's private key **on the admin workstation** and then moved
it. A single key existed in at least five places:

```text
admin workstation memory
  → S3 object            {ns}/hosts/{host}/private-key.pem
  → Fetcher Lambda       (read it to answer a CloudFormation custom resource)
  → CloudFormation       (custom-resource response body)
  → Secrets Manager      (indefinitely, updated in place on rotation)
  → SOPS file            (committed to your Nix repo, and its git history)
  → the host
```

Two consequences followed. Anyone holding `secretsmanager:GetSecretValue` could
impersonate any host, which substantially defeats the purpose of per-host
identities. And the key was permanently escrowed — deleting the SOPS file did not
un-leak it, because copies remained in S3, Secrets Manager, and git history.

**v3 removes the escrow entirely.** The key is generated by the host that will
use it, inside the key store, and nothing ever reads it back out for transport.
No S3 object, no Secrets Manager secret, no SOPS file, no per-host CloudFormation
stack. See [docs/MIGRATION-v3.md](docs/MIGRATION-v3.md) for how to migrate hosts
off the v2 arrangement.

Two supporting changes:

- `approve` **rebuilds** the certificate subject from the hostname being approved
  (self-signed mode) rather than copying it from the CSR. Since the CSR now comes
  from a host, trusting its contents would let a compromised host request a
  certificate naming a different host. In ACM PCA mode the template forces
  subject pass-through, so `approve` verifies the CN matches instead and refuses
  on mismatch.
- CSRs are checked for a valid self-signature (proof of possession) and a usable
  key type before signing.

## Key stores

| Backend | Key readable by | Protects against |
|---|---|---|
| `files` | any process running as the owning user, and root | transmission and escrow. The key exists in exactly one place |
| `macosKeychain` | nothing — marked non-extractable at import | additionally: exfiltration. The key cannot be copied off the host, even by you |

### What `macosKeychain` actually protects against

It stops the key being **copied**. An attacker with code execution as your user
can still *use* the key — they can invoke the credential helper, or any binary,
and obtain AWS credentials. What they cannot do is take the key with them, which
matters because a stolen key is a durable capability that survives you cleaning
up the host, whereas live code execution does not.

So it defends against backup theft, `scp` of a dotfiles directory, a curious
sync client, and an attacker who gets one-shot file read but not execution. It
does not defend against a compromised user account in the general case.

The key is imported with `security import -A -x`, meaning any application may use
it and it is non-extractable. It deliberately does **not** use `-T <binary>` to
restrict the ACL to the credential helper. Two reasons:

1. The nixpkgs `aws_signing_helper` is ad-hoc signed with no Team Identifier, so
   macOS binds the ACL to the binary's code-directory hash. Any rebuild — a
   nixpkgs bump, even to the same upstream version — produces a different hash
   and turns every credential fetch into an interactive GUI prompt. This was
   verified empirically against two store paths of the same v1.8.4 release.
2. The ACL would buy close to nothing anyway. It restricts *which binary* may
   sign, but any process running as the user can simply execute that binary.

The security gain is non-extractability, not the ACL.

### Known limitation

A key whose certificate was never installed cannot be deleted — `security`
provides no command to remove a bare private key, only an identity. `delete()`
removes the identity when present and always clears the index entry. Such an
orphan is inert: non-extractable, and unselectable without a certificate.

## Known gaps

These are real and currently unaddressed. They are listed because you should know
about them before deploying, not because they are acceptable.

### The self-signed CA private key is the weakest link

`~/.local/share/iam-ra/<namespace>/scopes/<scope>/ca-private-key.pem`, mode
`0600` in a `0700` directory.

This key mints certificates for every host in the scope. It is the
highest-value material in the system and the least protected — a plain file on a
workstation, with no passphrase and no hardware backing. Now that host keys are
no longer escrowed, this is unambiguously the thing an attacker should go after.

It is written with the mode set at `open` time, so it is never even transiently
readable by others, and every directory created to hold it is owner-only. That
closes the file-permission weaknesses, but not the fundamental one: a plain file
readable by your user account is only as safe as that account.

Mitigations available today: use `--ca-mode pca-new` or `pca-existing` so the CA
key lives in an AWS HSM and never exists in a filesystem, and treat the admin
workstation as a privileged host. Full-disk encryption helps against device
theft and not at all against a compromised account.

### No certificate revocation

Neither `host offboard` nor re-enrolment invalidates an already-issued
certificate. It keeps authenticating until it expires.

This is a gap in **this tool**, not in IAM Roles Anywhere. The service does
support revocation: you generate a CRL from your CA and push it with the
[`ImportCrl` API](https://docs.aws.amazon.com/rolesanywhere/latest/userguide/trust-model.html),
after which certificates are checked against it. What the service does *not*
support is fetching CRLs from a distribution point, or OCSP — so the CRL has to
be pushed explicitly. `iam-ra` neither generates nor imports one.

Until it does, the mitigation is short certificate lifetimes:

```bash
iam-ra host enroll web01 --role deploy --validity-days 7
```

That bounds the exposure window for a compromised or offboarded host to the
remaining validity. v3 makes re-enrolment cheap enough to run on a timer, which
is the intended answer.

### The default certificate validity is 365 days

Too long for a credential with no revocation path. It is a config default rather
than a storage problem, so it costs nothing to change — pass `--validity-days`.
The default remains 365 for backwards compatibility.

### Roles are scope-wide unless you opt in

By default any certificate chaining to a scope's trust anchor can assume any role
in that scope. `iam-ra role create --allowed-hosts` narrows this to a hostname
pattern, enforced in the trust policy against the certificate subject CN.

Caveats:

- This is only a meaningful boundary because keys are host-generated. If a host's
  key could be copied, so could its identity.
- If a Roles Anywhere profile has custom `attributeMappings` that omit the CN,
  IAM Roles Anywhere drops the tag and the condition evaluates false, denying
  access. Leave attribute mappings at their defaults unless you have a reason
  not to.

### `~/.aws/config` and wrapper scripts are world-readable

Both are `/nix/store` symlinks, and the store is world-readable by design. They
contain certificate paths, ARNs, and region — no secrets. Worth knowing if you
consider your role ARNs sensitive; they are not credentials.

### The `files` key store does not protect against a compromised user

It is a `0600` file. Any process running as that user, and root, can read it.
This is a deliberate tradeoff: `files` is the portable default and a large
improvement on v2, but it is not a hardware-backed store. Use `macosKeychain` on
macOS where it matters.

## Non-goals

- **Protecting against a compromised admin workstation in self-signed CA mode.**
  Whoever holds the CA key controls the scope. Use ACM Private CA if that is in
  your threat model.
- **Protecting against root on a host.** Root can read a `files` key, and can use
  a keychain identity.
- **Hiding certificates.** They are public by design. Commit them.
- **A Linux OS-keystore backend.** The credential helper's certificate-store
  support is a compile-time refusal stub on Linux, so there is nothing to
  integrate with. A backend would have to hand the helper a plain file anyway,
  which is what `files` already does.

## Verification

Security-relevant behaviour is covered by tests rather than convention, so a
refactor cannot silently regress it. Notably:

- `request` and `install` take no AWS context **in their function signatures**, so
  the host side provably needs no credentials.
- No returned value from any enrolment verb contains a private key.
- A signed certificate names the host being approved, not the host the CSR asked
  to be.
- `install` refuses a certificate whose public key does not match the stored key,
  including one superseded by a later `request`.
- The keychain key is genuinely non-extractable (asserted via `security export`).
- Private keys are written with the mode set at `open` time, so they are never
  transiently readable by others whatever the umask, and no directory on the path
  to a key is world-writable.
- Adding a keychain to the search list extends it and never replaces it.
- The default `--allowed-hosts *` emits **no** `PrincipalTag` condition, and the
  restricted form keeps the trust-anchor condition rather than replacing it.

Run the suite with `just test`, and the Nix module checks with `just check`.
